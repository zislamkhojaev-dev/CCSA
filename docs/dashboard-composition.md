# Дашборды: состав

Документ о **содержании** дашбордов — какие метрики показывать и как их визуализировать.
Внешний вид (визуальный язык) — в [dashboard-visual.md](dashboard-visual.md).

---

## Аудитория и принцип

**Пользователь — руководитель контакт-центра (КЦ).** Ему нужны **операционные показатели**,
готовые для решений, а не сырые данные (сырьё он при желании достаёт из БД сам).

Отсюда правила отбора метрик:

1. **Операционка, а не аналитика для продактов.** Каждая цифра → действие: кого обучить,
   какой критерий проседает, где растёт нагрузка.
2. **Всегда с контекстом.** Число само по себе бесполезно — нужны **динамика** и **дельта
   к прошлому периоду** («92%, ↑3% к прошлой неделе»).
3. **От общего к частному.** Сверху — сводка здоровья КЦ, ниже — разрезы (операторы,
   сценарии, критерии).
4. **Доверие к цифрам.** Показываем **покрытие** (какая доля звонков вообще оценена) —
   иначе «средний балл» вводит в заблуждение.

## Карта метрик (группы)

| # | Группа | Вопрос руководителя |
|---|--------|---------------------|
| A | Объём и нагрузка | Сколько звонков и какая нагрузка? |
| B | Качество | Как меняется качество обслуживания? |
| C | Нарушения и критерии | Что именно проседает в скрипте? |
| D | Операторы | Кто лучший, кого подтянуть? |
| E | Сценарии и классификация | По каким сценариям/темам звонки и их качество? |
| F | Здоровье пайплайна | Можно ли доверять цифрам? |

---

## A. Объём и нагрузка

| Метрика | Что показывает | Визуализация | Источник |
|---------|----------------|--------------|----------|
| **Обработано звонков** | Всего за период | KPI-число + дельта к пред. периоду | `Call` count |
| **Динамика звонков** | Поток по дням/часам | Line/area по дням; стек по направлению (вх./исх.) | `Call.call_timestamp` |
| **Распределение вх./исх.** | Баланс направлений | Donut или две KPI-плитки | `Call.direction` |
| **Средняя длительность (AHT)** | Среднее время разговора | KPI + спарклайн динамики | `Call.duration` |
| **Пиковые часы** | Когда нагрузка выше | Heatmap час × день недели | `call_timestamp` |

Идея: **heatmap «звонки по времени»** (как в e-commerce референсе) — руководитель сразу
видит пики и может планировать смены.

---

## B. Качество

| Метрика | Что показывает | Визуализация | Источник |
|---------|----------------|--------------|----------|
| **Средний балл** | Общий уровень качества | KPI (цвет по порогу) + дельта | `AnalysisResult.total_score` |
| **Динамика среднего балла** | Тренд качества | Line с **целевой линией** (target) | avg по дням |
| **Распределение оценок** | Сколько хороших/средних/плохих | Donut или стек-бар: >80% / 50–80% / <50% | бакеты score |
| **Доля высоких оценок** | % звонков «в норме» | Gauge / percent-виджет | score ≥ порог |

Идея: на линии динамики — **пунктирная целевая линия** (напр. цель 85%), чтобы видеть,
дотягивает КЦ до плана или нет.

---

## C. Нарушения и критерии — ядро речевой аналитики

Именно здесь дашборд отвечает «**что конкретно исправить**».

| Метрика | Что показывает | Визуализация | Источник |
|---------|----------------|--------------|----------|
| **Кол-во / доля нарушений** | Критичные срывы (грубость, обязат. фразы) | KPI + дельта | `AnalysisResult.is_violation` |
| **Проседающие критерии** | Какие пункты скрипта чаще не выполнены | Горизонтальные бары pass-rate по критериям, отсортированы по худшим | `CriterionResult` |
| **Топ типов нарушений** | Самые частые нарушения | Ранжированный список / бар | критерии-нарушения |
| **Динамика нарушений** | Стало лучше/хуже | Line по дням | по времени |

> **Это самое ценное для КЦ.** «Средний балл 78%» ничего не говорит; «критерий
> *"выявление потребности"* выполняется в 41% звонков» — прямое указание, чему учить.

Идея: **«тепловая» таблица критерий × оператор** (или критерий × команда) — сразу видно,
у кого какой блок скрипта провисает.

---

## D. Операторы

| Метрика | Что показывает | Визуализация | Источник |
|---------|----------------|--------------|----------|
| **Топ-5 лучших** | Кого поощрить / эталон | Список: аватар, имя, балл, дельта, мини-бар | avg score по оператору |
| **Топ-5 худших** | Кого подтянуть | Аналогичный список (красный акцент) | avg score по оператору |
| **Разброс по операторам** | Насколько ровная команда | Бар-чарт всех операторов или box/распределение | score по операторам |
| **Нагрузка по операторам** | Кто сколько берёт | Бар «звонки на оператора» | `Call.operator_id` |

Важно: рядом с баллом показывать **число звонков** — балл по 3 звонкам ≠ балл по 200.
Оператор с малой выборкой не должен попадать в «худших» несправедливо (порог min-выборки).

Идея: **combo-виджет оператора** — балл + объём + дельта в одной строке, сортировка
переключается (по баллу / по объёму / по нарушениям).

---

## E. Сценарии и классификация

| Метрика | Что показывает | Визуализация | Источник |
|---------|----------------|--------------|----------|
| **Разрез по сценарию** | Качество/объём по конкретному сценарию | Селектор сценария → пересчёт всех виджетов | `Scenario` / `AnalysisResult` |
| **Сравнение сценариев** | Где качество ниже | Бар «средний балл по сценариям» | группировка по сценарию |
| **Классификация звонков (темы)** | О чём звонки | Donut / горизонтальные бары по тегам | `Tag` / `CallTag` |
| **Темы × время** | Всплески тем | Heatmap тема × день | теги по времени |
| **Качество по темам** | Какие темы «болезненные» | Бар: балл по тегу | score × tag |

Идея: **глобальный селектор сценария** в шапке (как период) — весь дашборд
пересобирается под выбранный сценарий; «Все сценарии» по умолчанию.

---

## F. Здоровье пайплайна (доверие к данным)

| Метрика | Что показывает | Визуализация | Источник |
|---------|----------------|--------------|----------|
| **Покрытие (доля оценённых)** | % звонков, реально проанализированных LLM | Percent/gauge | `status = analyzed` / всего |
| **В очереди / ошибки** | Застряло в пайплайне | KPI + бейдж | `status` pending/error |
| **Свежесть данных** | Когда последнее обновление | Строка-хинт | max `created_at` |

> Без покрытия все остальные метрики теряют смысл: если оценено 10% звонков, «средний
> балл» — это балл по 10%, а не по КЦ.

## Дополнительные метрики речевой аналитики (предложение)

Многое можно извлечь **из транскрипта с таймингами** (`Transcription.utterances`) —
это то, чего нет в обычных QA-дашбордах и что усиливает именно «речевую» аналитику:

| Метрика | Смысл | Реализуемость |
|---------|-------|---------------|
| **Talk/Silence ratio** | Доля тишины в разговоре | Есть тайминги реплик |
| **Доля речи оператор/клиент** | Кто больше говорит (монолог оператора?) | По спикерам в utterances |
| **Перебивания (talk-over)** | Оператор перебивает клиента | Пересечение таймингов реплик |
| **Длинные паузы / dead air** | Заминки, «висяки» | Разрывы между репликами |
| **Темп речи** | Слишком быстро/медленно | Слов/сек по репликам |
| **Соблюдение обязат. фраз** | Приветствие, представление, скрипт-фразы | Поиск по тексту / критерий LLM |
| **Тональность / эмоция** | Негатив клиента, эскалации | Нужна доп. модель (roadmap) |
| **Повторные обращения** | Один клиент звонит снова | По номеру клиента |
| **Триггерные слова** | Мат, «жалоба», «отказ», «суд» | Уже частично есть (waveform-триггеры) |

Приоритет к внедрению (реализуемо на текущих данных):
**покрытие → проседающие критерии → talk-ratio/перебивания → триггерные слова**.

## Предлагаемый приоритет виджетов (сверху вниз)

Черновой скелет для «главного» дашборда руководителя:

```
KPI-ряд:  Обработано · Средний балл · Доля нарушений · Покрытие · AHT
────────────────────────────────────────────────────────────────────
Динамика звонков (line, стек вх./исх.)   │  Распределение оценок (donut)
────────────────────────────────────────┼───────────────────────────
Динамика среднего балла (line + target)  │  Проседающие критерии (бары)
────────────────────────────────────────┴───────────────────────────
Топ-5 лучших (список)  │ Топ-5 худших (список) │ Классификация тем (бары)
────────────────────────────────────────────────────────────────────
Пиковые часы (heatmap)                   │  Здоровье пайплайна (очередь/ошибки)
```

Глобальные контролы в шапке: **период**, **направление**, **оператор(ы)**, **сценарий**
(последний — новый, добавить к уже сделанным фильтрам).

## Реализуемость на текущих данных

Проверено по модели (`backend/app/models/entities.py`, `services/llm.py`):

- **По-критерийные результаты есть.** `AnalysisResult.criteria_results` — JSONB-словарь
  `{ключ_критерия: {score, passed, comment, status}}`.
  Pass-rate критерия = `passed=true` / `status=completed`
  (**`not_applicable` исключаем из знаменателя**).
- **Ключи критериев уникальны в пределах сценария** → по-критерийные метрики считаем
  **в разрезе сценария**; имя критерия — из `Criterion.name`.
- **Разрез по сценарию** — `Call.scenario_id` есть напрямую.
- **Готовый сигнал классификации** — `AnalysisResult.call_outcome` (LLM уже пишет исход
  звонка) и `client_pains` (боли клиента). Плюс ручные `Tag`/`CallTag`.
- **Покрытие** — `Call.status` (`analyzed` vs всего; `pending`/`error` — очередь/сбои).

Ограничение: `criteria_results` — JSONB, поэтому агрегации по критериям делаем через
JSONB-запросы Postgres либо досчётом в Python (объёмы дашборда это позволяют).

## Решения по открытым вопросам

| # | Вопрос | Статус | Решение |
|---|--------|--------|---------|
| 1 | Классификация звонков | ✅ решён | **Авто-категоризация тем LLM** отдельным шагом (не теги, не call_outcome) |
| 2 | Пороги «нормы» (цвета, target) | ✅ решён | **Настраиваемые в Settings** (порог + целевое значение) |
| 3 | Мин. выборка оператора для рейтинга | ✅ решён | **Без порога** — метрики за выбранный период, показываем всех |
| 4 | По-критерийные результаты в БД | ✅ решён | Есть (`criteria_results` JSONB); pass-rate по `passed`/`status`, разрез по сценарию |
| 5 | Речевые метрики | ✅ решён | В **бэклог** (talk-ratio, перебивания, паузы, темп, тональность) |

### Что следует из решений

**1. Классификация тем (новая возможность).** Отдельный шаг LLM присваивает звонку
**тему из настраиваемой таксономии**:
- **Таксономия настраивается в Settings** — руководитель задаёт список категорий
  (напр. «Оформление заказа», «Жалоба», «Возврат», «Консультация», «Спам»).
- LLM выбирает тему **из этого списка** (закрытый набор) + опция «Другое», чтобы не выдумывал.
- Хранение: новое поле `AnalysisResult.topic` (строка-ключ категории).
- Считается в пайплайне анализа; для уже оценённых звонков — задача до-разметки (backfill).
> Виджеты «Классификация тем» и «Качество по темам» строятся на `topic`;
> до backfill старые звонки попадают в «Не классифицировано».

**2. Настраиваемые пороги.** В `AppSetting` добавить ключи:
- порог «хорошо» (зелёный, по умолч. 80), порог «средне» (жёлтый, по умолч. 50);
- целевое значение (target-линия на динамике балла).
Дашборд читает их для цветов KPI, бакетов распределения и целевой линии. Раздел в Settings.

**3. Рейтинги операторов — без min-выборки.** Топ-5 лучших/худших считаются по всем операторам
за выбранный период. Рядом с баллом всё равно показываем **число звонков** (контекст),
но фильтр по минимуму не применяем.

## Настройки дашборда (раздел в Settings)

Всё настраиваемое собираем в один раздел «Дашборд / Качество»:

| Настройка | Тип | По умолчанию | Хранение |
|-----------|-----|--------------|----------|
| Порог «хорошо» (зелёный) | число % | 80 | `AppSetting` |
| Порог «средне» (жёлтый) | число % | 50 | `AppSetting` |
| Целевой средний балл (target) | число % | 85 | `AppSetting` |
| Таксономия тем | список строк | базовый набор | `AppSetting` (JSON) |

## План реализации (полный скоуп)

Делаем всё; порядок — от фундамента к виджетам.

### Фаза 1 — Фундамент (бэкенд)
1. Настройки: пороги (хорошо/средне/target) + таксономия тем в `AppSetting` + API + раздел в Settings UI.
2. Классификация: поле `AnalysisResult.topic` (миграция), шаг LLM выбирает тему из таксономии,
   задача backfill для старых звонков.
3. Метрики-агрегаты: pass-rate по критериям, критерий×оператор, покрытие, темы —
   расширить `dashboard_metrics.py` (с учётом уже сделанных фильтров период/направление/оператор/сценарий).

### Фаза 2 — Новые типы виджетов (фронтенд)
4. Проседающие критерии (горизонтальные бары pass-rate).
5. Топ-5 лучших / худших операторов (списки с баллом, объёмом, дельтой).
6. Динамика ср. балла с target-линией; распределение оценок (donut по настраиваемым порогам).
7. Классификация тем (бары) + качество по темам.

### Фаза 3 — Продвинутое
8. Тепловая таблица критерий × оператор.
9. Heatmap пиковых часов (час × день).
10. Глобальный селектор сценария в шапке (пересбор дашборда под сценарий).
